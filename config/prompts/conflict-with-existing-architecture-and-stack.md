# Конфликт с существующей архитектурой и стеком

Ещё ИИ может предложить решение, которое не вписывается в текущий стек, требует неоправданных изменений или нарушает архитектурные принципы.

## Типичные проблемы

- Рекомендует Hibernate, когда проект использует Spring Data JDBC.
- Советует добавить новый HTTP-клиент (OkHttp), когда весь проект на WebClient.
- Предлагает полностью переписать блокирующий код на реактивный без учёта унаследованного кода и рисков.
- Рекомендует менять публичные API без обратной совместимости.

## Как действовать

Используйте AGENTS-файл с описанием стека, архитектурных решений и ограничений. Явно указывайте ограничения в промпте. Вот как они могут выглядеть:

- «Нельзя менять публичные интерфейсы».
- «Нельзя добавлять новые внешние зависимости без согласования».
- «Нужна обратная совместимость для всех миграций базы данных».
- «Миграция должна быть постепенной, без остановки сервиса».

## Многокомпонентные задачи в сложной архитектуре

Реальные задачи редко касаются одной области. Нужно учитывать микросервисы, очереди, Kubernetes, наблюдаемость, SLO и работу в нескольких регионах.

Задача «Реализовать обработку 100 тысяч задач в час» требует учёта:

- Архитектуры (микросервисы vs монолит).
- Очередей (Kafka/RabbitMQ).
- Масштабирования (Kubernetes HPA, Spring Cloud LoadBalancer).
- Наблюдаемости (метрики Micrometer, дашборды Grafana, OpenTelemetry).
- Обработки ошибок и retry-политики.
- Идемпотентности и гарантий доставки (at-least-once/at-most-once/exactly-once).
- Мониторинга и алертинга.

### Как действовать

Разбивайте сложную задачу на подзадачи через цепочки промптов (паттерн Plan/Act). Используйте ИИ для каждого аспекта отдельно (сначала архитектура, потом масштабирование, потом наблюдаемость), затем интегрируйте решения. Просите указать плюсы и минусы каждого подхода.
